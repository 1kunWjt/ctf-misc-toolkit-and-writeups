## 一、题目长什么样（先建立直觉）

附件只有一个 `机密文档.zip`，里面**只有一条**记录，名字非常挑衅：

```
the_secret_you_never_ever_know_hahahaha.zip     # 43 字节，method=0（store），flag=0x0001
```

这一条自己又是一个 `.zip`——典型套娃。`flag_bits=0x0001` 意思很直接：**这条记录带口令**；压缩方式还是 `store`（不压缩），所以 `compress_size` 只比 `file_size` 多 12 字节——多的正是 PKZIP 传统加密（ZipCrypto）的加密头。

拿到手时"这题是什么"只有三种可能，而三条路打法完全不同：

```
① 伪加密    —— 头部 flag 说是加密，其实数据是明文，改字节即可解
② 弱口令    —— 真加密，但口令在字典里
③ 明文攻击  —— 真加密，口令猜不到，靠已知明文把 96 bit 内部密钥反解出来
```

这道题的信息量全在"判出是哪一种"上，判错一种后面全是白干。本篇完整记一个**失败的判定过程**：结论是 ③，而 ③ 没在限时内做完——但"怎么把 ①②③ 排除到只剩一个"这段过程是可以直接复用的。

## 二、思路总览

先给结论：**这不是伪加密，是真 ZipCrypto；口令不在小空间里；只能打明文攻击。**

```
1) 逐字段解析两个头（本地文件头 PK\x03\x04 / 中央目录 PK\x01\x02）
   -> flag 全 0x0001 且一致、csize-usize=12、data_off=73、CD=0xec5a、EOCD 算式自洽
2) 打伪加密判据
   -> flag 不一致？没有。csize == usize？没有（差 12）。两条特征都不成立
3) 判数据区是不是真密文
   -> 熵 7.9966、256 种字节全出现、无任何 PK 签名、deflate/bz2/lzma 全解不开
4) 口令空间打穿
   -> 手挑 27 + 全小写 1~4 位（475,254）+ 纯数字 0~999999，共 1,475,254 次全 MISS
5) 剩下唯一一条路：已知明文攻击（bkcrack），本篇止步于此
```

第 4 步敢下"口令不可猜"的结论，前提是我先把 `ZipCrypto` 实现和标准库 `zipfile._ZipDecrypter` 逐字节对拍过（3.4）。**实现没错，所以"爆破失败"这个结论才可信**——很多人的"爆破失败"其实是校验条件写错了。

## 三、逐步复现

### 3.1 第一步：把两个头逐字段算清，顺手验版面算术

用 `struct` 直接读本地头（`PK\x03\x04`，flag 在偏移 6）、中央目录（`PK\x01\x02`，flag 在偏移 8）、EOCD（`PK\x05\x06`）。这一步的真正目的是**排除"文件被人改过"**：三处版面算术对得上，才说明拿到的是原件。

`solve/01_inspect.py` 真实输出：

```
name                                       cdflag method csize   usize   lhoff
the_secret_you_never_ever_know_hahahaha.zip 0x0001 0x0000   60433   60421        0
    -> local header flag = 0x0001   MATCH
[raw central directory] first PK\x01\x02 at 0xec5a  cd_flag=0x0001
[FAIL] testzip: RuntimeError: File 'the_secret_you_never_ever_know_hahahaha.zip' is encrypted, password required for extraction
```

`solve/04_parse.py` 把算术一次算完（节选）：

```
[EOCD] at 0xecd7   n_this=1 cd_size=125 cd_off=60506 cmt_len=0
  check: cd_off + cd_size + 22 = 60653  (file size 60653)  OK
[CD 0] at 0xec5a   flag=0x0001 (bit0 encrypted=1, bit3 data-desc=0)  method=0
  crc32 = 0x0c583fae   csize / usize = 60433 / 60421  (diff 12)
  nlen/elen/clen = 43 / 36 / 0    local hdr offset = 0 (0x0)
[LH] at 0x0   sig=04034b50 flag=0x0001 method=0  crc=0x0c583fae
  csize=60433 usize=60421 nlen=43 elen=0
  layout: 30 + 43 + 0 => data_off = 73 (0x49)
  data_off + csize = 60506 ; CD starts at 60506 (0xec5a) ; gap = 0
```

怎么读：

- `flag=0x0001`（bit0=encrypted）在本地头与中央目录**完全一致**（`MATCH`）。伪加密的经典判据是"两处 flag 不一致"，这里不成立。
- `method=0` → store 不压缩，所以数据区长度 = 明文长 + 12，`60433 - 60421 = 12` 精确对上 ZipCrypto 的 12 字节头。
- `data_off=73`、`73 + 60433 = 60506 = CD 起点`、`60506 + 125 + 22 = 60653 = 文件长度`，首尾相接、`gap = 0`：**文件是原样的**（若有人做过 `09 00 → 00 00` 之类的伪加密修补，这里一定错位）。
- 中央目录有 `elen=36` 的 NTFS 时间戳扩展（`0a 00 20 00 ...`），而**本地头 `elen=0`**。这是 Windows「发送到→压缩文件夹」的正常产物，但它埋了一个坑（第五节第 2 条）。

### 3.2 第二步：伪加密判据为什么在这题不成立

伪加密的本质是**头部说加密、数据其实是明文**，只有两条成因，对应两条判据：

| 判据 | 伪加密的表现 | 本题实测 |
|---|---|---|
| 两处 flag 不一致 | 本地头 `bit0=1`、中央目录 `bit0=0`（或反之） | 两处都 `0x0001`，`MATCH` |
| `csize == usize` | 没有 12 字节加密头，长度相等 | `60433 vs 60421`，差 12 |

两条都不成立（数据区也认不出明文结构，见 3.3），三条一起否掉。**这题的第一个诱惑就是错的**：它长得很像伪加密（要口令、又是套娃压缩包），但它是真加密。顺带一个教训（见第五节第 4 条）：很多 WP 讲伪加密会写"把 `09 00` 改成 `00 00`"，而 `0x0009` 只是某类工具的残留值，**判据要以自己 `struct.unpack` 出来的值为准**。

### 3.3 第三步：证明数据区就是密文

三件事一起做：算熵、扫签名、绕开 `method` 字段直接试解压（如果 `method=0` 是撒谎的，把数据区喂给 zlib 就该炸出明文）。

`solve/05_analyze.py` 真实输出：

```
[INFO] payload region: 0x49..0xec5a  (60433 bytes)
[ENTROPY] 7.9966 bits/byte   (8.0 = 完全随机；文本/zip 通常 < 6.5)
[ENTROPY] distinct byte values = 256/256 ; max bucket = 280
[SCAN] b'PK\x03\x04' / b'PK\x01\x02' / b'PK\x05\x06' / b'\x89PNG' -> none
[TEST] empty password: decrypted header last byte = 0x2e (want 0x0c)
[TRY] raw deflate / bz2 / lzma on payload (offset 0 and 12)
  [MISS] off=0  deflate -> error      [MISS] off=0  bz2 -> OSError    [MISS] off=0  lzma -> LZMAError
  [MISS] off=12 deflate -> error      [MISS] off=12 bz2 -> OSError    [MISS] off=12 lzma -> LZMAError
```

读法：熵 7.9966、256 种字节值全出现、最大桶只有 280（60,433/256 ≈ 236，分布极均匀）——典型密文；六种"直接解压"组合全失败，说明 `method=0` 没撒谎，也没有"12 字节垃圾前缀"这种伪加密残留；空口令解密后头尾字节是 `0x2e`，而 `CRC32 >> 24 = 0x0c`，不等 → 不是空口令。

判定到此闭环：**真 ZipCrypto，12 字节头，明文 60,421 字节，CRC = 0x0c583fae**。

### 3.4 第四步：先证明自己的 ZipCrypto 没写错，再谈"爆破失败"

这是本篇最值得抄走的方法论。爆破失败有两种可能：口令不在空间里，或者**校验条件写错了**——后者更常见，而且会让人毫无根据地扩字典。所以先拿标准库 `zipfile._ZipDecrypter`（CPython 自带的 ZipCrypto 解密器）当裁判，对拍密钥流：

```python
std  = zipfile._ZipDecrypter(pwd)(bytes(24))   # 解密 24 个 0 -> 直接就是密钥流
mine = ZipCrypto(pwd).keystream(24)            # 自己的实现，同样喂 24 个 0
assert std == mine
```

`solve/06_selftest_fix.py` 真实输出：

```
== A. 和标准库 zipfile._ZipDecrypter 对拍密钥流 ==
  pwd=b'test123'   match=True  ks[0:8]=63 d7 f9 a7 28 93 3a b2
  pwd=b''          match=True  ks[0:8]=ab db 04 4b 12 ce 7c 66
  pwd=b'Passw0rd!' match=True  ks[0:8]=6d bd f2 2a 6d 09 3a ce
== B. 正确写法造的真 ZipCrypto zip ==
  zipfile 读取 : PASS      错误口令对照 : RuntimeError: Bad password for file 'probe.txt'
```

三条密钥流逐字节相同，自己造的真加密 zip 能被标准库读回、错口令会被拒。**实现正确性到此可以签字**，后面字典打不中只能是口令本身不在空间里。顺带说清 `05_analyze.py` 里那个刺眼的 `[SELFTEST] FAIL`：不是算法错，是探针 zip 自己造错了（第五节第 3 条）。

### 3.5 第五步：把口令小空间打穿，然后转明文攻击

`solve/03_crack.py` 用纯 Python 实现 ZipCrypto（不依赖 pycryptodome），校验两重：① 解密后 12 字节头的**第 12 字节** `== CRC32 >> 24`；② 再解前 16 字节，要求 `[12:16] == b'PK\x03\x04'`（内层是 zip，明文第 13 字节起必须是本地头签名）。第二条是本题特有的强过滤——单靠①，1/256 的命中率意味着 147 万次会撞出约 5,700 个假阳性。

真实运行输出：

```
[INFO] entry : the_secret_you_never_ever_know_hahahaha.zip
[INFO] CRC32 : 0x0c583fae  -> expected check byte 0x0c
[INFO] enc[0:12] : 09 06 37 37 e1 07 7f 6f 52 c1 ec 52
[MISS] 27 hand-picked candidates rejected
[MISS] lowercase 1-4  (475254 tries)
[MISS] numeric 0-999999  (1475254 tries total)
```

手挑列表含：条目名、去 `.zip` 的词干、`机密文档`、`jimiwendang`、`the_secret`、`you_never_ever_know`、`hahahaha`、`dasctf`、`DASCTF2024`、`123456` 系列、`password`、`admin` 等 27 个——全灭。合计 **1,475,254** 次、两重校验零命中，可以定论：口令不是"短 ASCII / 常见词"。这也符合题型设计——口令若可猜，就不必给一个 60 KB 的 store 型 zip。

前期工作全部完成，缺的只有最后一步：Biham–Kocher 已知明文攻击（bkcrack 那套）——为什么没做，见下节。

## 卡点与正解方向

### 已确认的事实（可直接复用）

| 事实 | 值 | 证据脚本 |
|---|---|---|
| 加密方式 | ZipCrypto，`flag=0x0001`，本地头/中央目录一致 | `01_inspect.py` |
| 压缩方式 | `method=0`（store），不压缩 | `04_parse.py` |
| 密文区 | `0x49 .. 0xec5a`，60,433 字节；明文 60,421 字节 | `04_parse.py` / `05_analyze.py` |
| CRC32 / 空口令 | CRC32 `0x0c583fae` → 头校验字节 `0x0c`；空口令头尾字节 `0x2e ≠ 0x0c`，不是空口令 | `03_crack.py` / `05_analyze.py` |
| 实现正确性 | 与 `zipfile._ZipDecrypter` 三条密钥流逐字节相同 | `06_selftest_fix.py` |
| 口令空间 | 手挑 27 + 小写 1~4 位 475,254 + 数字 0~999999 全 MISS | `03_crack.py` |

### 卡在哪

1. **没有 bkcrack / pkcrack 二进制，本机无网络也无法编译下载。** 纯 Python 重写 Z 约减（2³⁸ 级、带强剪枝）不是限时内能写完并调对的东西；而"先猜口令再验"的路线已被 3.5 的 147 万次尝试证明走不通。
2. **已知明文只有"结构假设"，没有"确认明文"。** 我确定内层是 zip（明文前 4 字节 `50 4b 03 04`），本地头的 `nlen`（偏移 26）、`elen`（偏移 28）也是小端小数值；但**从偏移 30 起的 43 字节文件名是推断**（按题目命名习惯猜它与外层条目同名）。这 43 字节若猜对是极强的已知明文（bkcrack 只要 12 字节、其中 8 字节连续），猜错就等于零。

### 正解方向（按性价比排序）

1. **有 bkcrack 的环境直接打**：已知明文分两块给，`head.bin` 放本地头里确定的部分，`name.bin` 用 `-x 30` 钉在偏移 30；拿到 96 bit 密钥后直接解出内层 zip 再继续剥：

   ```
   # 待执行（本机没有 bkcrack）
   bkcrack -C 机密文档.zip -c the_secret_you_never_ever_know_hahahaha.zip -p head.bin -x 30 name.bin
   bkcrack -C 机密文档.zip -c the_secret_you_never_ever_know_hahahaha.zip -k <k0> <k1> <k2> -d inner.zip
   ```

2. **先用 12 字节标准头单点试**：内层若是常见工具打的包，本地头前 12 字节常是 `50 4b 03 04 14 00 00 00 00 00` 这类固定前缀（`method=0` 时第 8~9 字节为 `00 00`）。这条不需要等文件名假设验证，比第 1 条更快、更弱。

3. **交叉验证口令线索**：条目名 `the_secret_you_never_ever_know_hahahaha` 是明显的挑逗式命名，通常意味着"口令不在名字里"。有网时按赛题名 + 这句话检索公开 WP 属常规操作；**本机无网（`web_search` 各引擎均超时），这一步没做**，所以本篇不给任何"听说口令是 xxx"的说法。

4. **补工具**：把 bkcrack 放进常备工具清单（`11-工具与速查`）。这题本质是工具题，不是算法题——手写 Z 约减不值这个时间。

## 四、关键知识点

| 概念 | 是什么 | 这题为什么用它 | 以后在哪还会遇到 |
|---|---|---|---|
| 本地头 vs 中央目录 | 每条记录在文件头有一份头（`PK\x03\x04`），文件尾中央目录（`PK\x01\x02`）再存一份 | 伪加密的判据就是"两处 flag 是否一致"，必须两边都读 | 所有 zip 伪加密题、zip 结构修复 |
| general purpose bit flag | 本地头偏移 6、中央目录偏移 8 的 2 字节位域 | `bit0=1` 就是"带加密"；`bit3=1` 表示长度写在数据描述符里 | 伪加密、data descriptor 缺失 |
| ZipCrypto 12 字节头 | 密文前 12 字节，第 12 字节 = 明文 CRC32 高字节 | `csize - usize == 12` 是它存在的硬证据，也是"非伪加密"的判据 | 所有 ZipCrypto 题；`csize==usize` 才是伪加密 |
| ZipCrypto 密钥流 | 3 个 32 bit key（`0x12345678/0x23456789/0x34567890`）经 CRC 表与乘加推进 | 既能做口令试探，也是明文攻击的输入 | 压缩包爆破、明文攻击 |
| 已知明文攻击 | 由 ≥12 字节（含 8 字节连续）明文反推 96 bit 内部密钥 | 口令不可猜时唯一的正路；拿到密钥后可解任意一条 | 所有 ZipCrypto 强口令题 |
| `zipfile._ZipDecrypter` | CPython 自带的 ZipCrypto 解密器 | 当裁判对拍密钥流，30 秒证明自己实现对不对 | 任何自写流密码/古典密码的验证 |

## 五、踩坑与陷阱

1. **`csize > usize` 被当成伪加密**：伪加密的干净特征是 `csize == usize`（没有 12 字节头）；`csize - usize == 12` 恰恰说明**真加了 12 字节头**。正确顺序：先比两处 flag，再算差值，最后看数据区熵——只看 flag 会误判。
2. **拿中央目录的 `elen=36` 去算本地数据偏移**：本地头 `elen=0`，若用中央目录的值算 `data_off` 会得到 `73 + 36 = 109`，然后"发现数据区末尾与中央目录重叠"这种假异常，白折腾半天。**`data_off` 只认本地头。**
3. **`[SELFTEST] FAIL` 被当成算法写错**：`05_analyze.py` 自造探针 zip 读不回来，报 `Bad password`，真正原因两条都与算法无关——(a) 12 字节头的校验字节位置错了（PKZIP 规范要求它在**最后一字节**）；(b) 更隐蔽：它把 `decrypt()` 当 `encrypt()` 用，而 ZipCrypto 的密钥推进必须喂**明文**（解密时输出就是明文，所以"喂输出"碰巧对；加密时输出是密文，第 2 个字节起全跑偏）。正确姿势是对拍标准库，而不是自己造加解密闭环。
4. **拿别人的常量表当判据**：规划笔记里写着"伪加密 `09 00` → `00 00`"，而本题实测 flag 是 `0x0001`。`0x0009` 只是某类工具造伪加密的常见残留，不是定义；**判据永远以自己解出来的字段为准。**
5. **单靠"头校验字节"爆破会被假阳性淹没**：1/256 的命中率意味着 147 万次约 5,700 个假命中，必须加第二重条件（本题：解开后第 13 字节起是 `PK\x03\x04`，或直接校验全明文 CRC）。

## 六、赛场 20 分钟行动清单

1. `python solve\01_inspect.py`：列条目、比两处 flag、打印 `csize/usize`。—— 1 分钟，先定性伪加密还是真加密。
2. `python solve\04_parse.py`：验版面算术（`data_off`、`CD`、`EOCD` 三处相扣）。不自洽 → 文件被改过，先查这个；`csize-usize == 12` 且 flag 一致 → 真 ZipCrypto，跳到第 3 步。
3. 用 `zipfile._ZipDecrypter` 对拍自己的实现（30 秒），再跑小字典 + 纯数字。**只给 5 分钟**。
4. 口令打不中 → 立刻切明文攻击，第一件事是确认**已知明文**：内层文件类型给了什么固定头？`50 4b 03 04` 只有 4 字节，够不够？不够就从 `nlen`/`elen` 加命名习惯去推文件名。
5. 有 bkcrack 就用 `-x` 钉偏移打分块明文；没有就**马上跳题**——手写 Z 约减不值这个时间。
> 超过 20 分钟没进展就跳题。这题的分数在"判对类型 + 敢跳"上，不在硬啃。
