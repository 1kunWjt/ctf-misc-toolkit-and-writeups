## 一、题目长什么样（先建立直觉）

题面只有一句"好多漂亮的壁纸，赶快挑一张吧"，配一个 pcapng。按这类题的常规套路，抓包里应该是**大量图片下载流量**，flag 被切成两半：一半塞在某张图的 EXIF 里，另一半藏在某条 TCP 流的正文里，拼起来才是完整 32 位。

参考解给出的规模是：附件是一个 zip 里的 `results.pcap`（14,222,652 B），导出后得到 **419 个 HTTP 图片对象**与 **150 个 FTP 数据对象**。

而现场这份 `wallpaper.pcapng` 是 18.2 MB、100,408 帧的抓包。从体积看"像个大流量题"，但一验内容就发现它连一张 JPEG 都没有——这构成了本篇的主线：**先证明附件不对，再写清正解该怎么走**。

## 二、思路总览

正确链路（依据参考解，逻辑上自洽）：

1. 批量导出 HTTP 响应体，按 `Content-Type` / 文件魔数切成独立文件；
2. 逐个读 EXIF（等价 `exiftool *.jpg | grep -i flag`），在某一页的注释字段拿到前半段 `flag{ae58d0408e26e8f`；
3. 按 `tcp.stream eq 114` 追踪那条流，重组后在正文里拿到后半段 `26a3c0589d23edeec}`；
4. 拼接：15 位 + 17 位 = 32 位十六进制，正好一个 MD5 的长度。

本机核对的结果是：第 1 步在本附件上就断了——没有图片可导。所以本篇的重点从"怎么解"变成"**怎么用三条硬指标在 5 分钟内判断附件是否对**"，这也是实战里最值钱的一步。

## 三、逐步复现

### 3.1 第一步：先看规模与分布

用纯 Python 解 pcapng 块（`overview.py`），得到：

```
frames 100408      文件 18,265,276 B
ip_proto [(6, 100244), (17, 51)]
top ports [(80, 85347), (445, 14844), (15539, 631), (16432, 221), ...]
streams 8530
```

两个数字立刻可疑：**80 端口 85,347 个包**（HTTP 短连接，一图一连），**445 端口 14,844 个包**（SMB）。壁纸站不会同时产生上万条 445 短连接，这说明抓包里混进了扫描/蠕虫类噪音。

### 3.2 第二步：三条硬指标，判定"没有图片"

不要凭感觉，用可复核的字节级指标：

| 检验项 | 命令/方法 | 本附件结果 | 壁纸题应有 |
|---|---|---|---|
| JPEG 魔数 | 全文搜 `FF D8 FF` | **0 次** | 419 个左右 |
| EXIF 段 | 全文搜 `Exif\0\0` | **0 次** | 至少 1 个藏 flag |
| flag 前半段 | 搜 `ae58d0408e26e8f` | **0 次** | 应存在 |
| flag 后半段 | 搜 `26a3c0589d23edeec` | **0 次** | 应存在 |
| FTP 取文件 | 搜 `USER` / `RETR` | **0 次** | 150 个数据对象 |

也就是说：JPEG 段不存在、EXIF 段不存在、参考答案里的两段 flag 片段也不存在。**18 MB 里一个 `FF D8 FF` 都没有**，那就不是"图多到看不过来"，而是"根本没有图"。

> 这一条比"翻不出来"强得多：`FF D8 FF` 是 JPEG 的文件头，只要有一张图必然出现；0 次是决定性反证。

### 3.3 第三步：那这包到底是什么

把 HTTP 请求行和状态码统计出来（按四元组重排 TCP）：

```
methods  HEAD 38728 | POST 126 | GET 36
status   404 38674 | 302 132 | 200 47 | 403 33 | 301 5
unique paths 38723
```

`HEAD` 占了 99.6%，38,723 个唯一路径——这是**目录爆破**，不是看壁纸。再从 200 的响应里抠页面标题：

```
天融信杯信息安全挑战赛
登录到Hello World - Hello World - Powered by Typecho
Index of /build/install
typecho-logo
404 Not Found
```

服务器指纹 `Server: Apache/2.4.27 (Win64) PHP/5.6.31`，响应时间戳 `Fri, 02 Nov 2018 09:21:32 GMT`。

结论：这是一份 **2018 年天融信杯期间的 Web 扫描抓包**，扫描者 `192.168.128.1`，目标 `192.168.128.145`，目标是站点根目录下的 `/build/`（一个 Typecho 博客，连 `install` 目录的目录列表都是开的）。

顺带说明为什么"看也看不到内容"：扫描器全程用 `HEAD`，服务器只回响应头，**没有正文**。没有正文，就不可能有"从正文里抠出来的文件"。

### 3.4 第四步：那 445 端口在干什么

14,844 个 445 包，全是单包 SYN，没有握手、没有 payload。按四元组首现顺序编号（与 Wireshark 的 `tcp.stream` 同规则）后抽查：

```
stream 0    : 100.183.251.126:445 ↔ 192.168.128.145:50228
stream 114  : 115.20.252.119:445  ↔ 192.168.128.145:49810   payload 段 0
```

`192.168.128.145` 既被别人扫 445，也在往外打 445，是典型的**永恒之蓝式蠕虫**传播形态。它也解释了为什么"stream 编号对不上"：这类单包流会占用编号，把 HTTP 流的序号整体顶走。

参考解里那句 `tcp.stream eq 114` 在本文件里正好落在一个 445 扫描流上，且该流 payload 为 0 字节——**编号体系没问题，是文件内容不对**。

### 3.5 第五步：现场脚本试过什么

现场留下的脚本就是这一段工作的痕迹：

| 脚本 | 做了什么 | 结果 |
|---|---|---|
| `overview.py` | 块解析 + 端口/会话统计 | 确认 80 + 445 两条主线 |
| `deep.py` | 按服务端口统计 payload、列请求行、找最大响应 | 没有图片响应体 |
| `non404.py` | 只看非 404 的请求 | 全是 `HEAD`，无正文 |
| `pick.py` / `peek_streams.py` | 抽样看流内容 | 都是响应头 + 少量 HTML |
| `findflag.py` | 在**所有**重组流里正则搜 `flag{...}` 与 `edeec}` | 命中 0 |
| `str610.py` | 单独看 610/611 两条大流 | 是 keep-alive 复用的扫描流，非图片 |

`findflag.py` 这一段是关键证据：它不是"猜某个流"，而是把所有 8,530 条流两个方向都重排一遍、逐条正则扫 `flag\{[^}]{0,80}\}?`，仍然 0 命中。这就把"藏在某条流里但我没找到"这条路彻底排除了。

## 四、关键知识点

| 概念 | 是什么 | 这题为什么用它 | 以后在哪还会遇到 |
|---|---|---|---|
| JPEG 魔数 | 文件头固定 `FF D8 FF` | 一张图都没有时，它是唯一可信的计数依据 | 任何"导出对象"题的自检 |
| EXIF 藏在哪 | JPEG 的 `APP1` 段，字段如 `ImageDescription` / `UserComment` | 壁纸题标准的藏 flag 位 | 图片隐写、社交平台溯源 |
| `HEAD` 与 `GET` | 只请求响应头 / 请求完整响应 | 99.6% 是 HEAD → 抓包里天然没有正文 | 扫描器识别、蜜罐日志 |
| `tcp.stream` 编号规则 | 按四元组首现顺序递增，含所有端口 | 编号会被 445 单包流顶走，跨文件不可复用 | 一切引用流号的解法 |
| 附件指纹核对 | 时间、UA、站点标题、端口组合 | 5 分钟判断"这是不是同一道题" | 多题并行、附件下错的场合 |

## 五、踩坑与陷阱

1. **只看体积就开工**。18 MB 很容易让人默认"图很多"，实际是 38,674 个 404 响应撑起来的。
2. **按参考解的流号硬找**。`tcp.stream 114` 在本文件里是 445 扫描流，追下去只会追到 0 字节 payload。
3. **把 `HEAD` 响应当正文解**。扫描流里 200 的响应只有头，`Content-Length` 是给 GET 用的，按 CL 切会切出一堆 0 字节。
4. **字符串跨包就判"没有"**。单包 strings 搜不到 `flag{` 还不足以证明没有；必须**先重排再搜**。本文件是重排后仍为 0，结论才算立得住。
5. **把 445 当噪音删掉**。它确实没 payload，但它的存在改变了流编号，删了反而对不上号。

## 卡点与正解方向

**已确认的事实**

1. 现场附件是 18,265,276 B 的 `wallpaper.pcapng`，100,408 帧、8,530 条 TCP 流，80 端口 85,347 包、445 端口 14,844 包。
2. 全文没有 `FF D8 FF`（JPEG 魔数）、没有 `Exif\0\0`、没有 `flag{`、没有参考答案里的任一段片段、没有 `RETR`。
3. 该抓包的真实身份是 2018-11-02 对 `192.168.128.145`（Typecho 站点，`/build/`）的一次 `HEAD` 目录爆破，外加 445 端口蠕虫式扫描。
4. 扫描器全程 `HEAD`，服务器没有返回任何可提取的文件正文，因此**不存在隐藏图片/文件**这一通道。

**卡在哪**

- 题面要求的"419 个图片对象 + 150 个 FTP 数据对象"在本文件里完全不存在，参考解第一条命令（导出图片）就无从执行；
- 参考解引用的 `tcp.stream 114` 在本文件里是 `115.20.252.119:445 ↔ 192.168.128.145:49810` 的 SYN，payload 为 0，给不出 flag 后半段；
- 因此这张附件上复现不出答案，`flag{ae58d0408e26e8f26a3c0589d23edeec}` 只能作为"参考答案"记录，不算本机战果。

**正解方向（拿到正确附件后按此执行）**

1. 附件应是 zip 内的 `results.pcap`（约 14.2 MB），解压后先核对：`FF D8 FF` 计数应在数百量级，且存在 `FTP` 控制通道（`USER` / `PASS` / `PORT` / `RETR`）。
2. 导出图像对象：按 TCP 流重排 → 按 `Content-Type: image/*` 或魔数切分 → 落盘为独立文件。
3. 批量读 EXIF：`exiftool -a -u -g1 *.jpg | grep -i -E "flag|comment|description"`，拿到 `flag{ae58d0408e26e8f`。
4. 定位后半段：先 `tcp.port == 80 || tcp.port == 20` 过滤后再编号，或直接全局搜 `edeec}`，比死磕流号可靠。
5. 拼接并验形：15 + 17 = 32 位十六进制，符合 MD5 长度，形如 `flag{32 hex}`。

**下次遇到同类题的判据**

先算"每 MB 里的 JPEG 数"。正常壁纸题在 0.02 张/KB 这个量级；本附件是 0 张 / 18 MB，一秒就能判死。附件核对永远排在解密之前。
