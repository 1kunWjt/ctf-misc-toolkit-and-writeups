## 一、题目长什么样（先建立直觉）

附件解开是两样东西，性质完全不同：

- `个人信息数据规范文档.pdf`（103,931 字节，1 页）——**规则**。正文全是“保存为 __ 文件，文件编码为 __，列名为 __”这样的空壳，关键值一个都不在字面上；
- `ds-data.zip`（3,173,978 字节）——**数据**。解出来是一个完整的 MySQL 数据目录：`ibdata1`、`ib_logfile0/1`、`mysql/`、`performance_schema/`、`sys/`、`person/`。业务库是 `person`，里面只有一张表 `data`（`data.frm` 12,874 字节 + `data.ibd` 9,437,184 字节）。

也就是说，这题的形状是：**规则在文档里但要“挖”，数据在文件里但要“解”**。而且数据显示成一个诡异的中间态 —— 有的行是明文，有的行被 Base32/Base64/Base85 编过，到底用哪种由同一行的 `cryptoType` 字段自己声明。本机没有 `mysqld`、没有 `docker`，不能“起库导表”，只能直读 `.ibd` 的页结构 —— 这恰好是数据恢复工程的正题：页 → 记录 → 字段。

## 二、思路总览

1. 用纯标准库把 PDF 的文本层抽出来（`01_pdf_extract.py`）→ 只有中文，ASCII 全丢；
2. 回到 PDF 对象层：内容流 `obj 4` 一共 117 个 `BT`/`Tf`/`Tj`，字体资源名是 `C1/TT1/TT3/TT5/TT6` —— **ASCII 一直在文字层里**，是按资源名查 CMap 失败被整段丢掉的；
3. 把 Image XObject 抽成 PNG（`02_pdf_images.py`）→ `obj 17` 是 2002×194 的“格式参考”表格截图，与文字层里的三行示例互为印证；
4. 解析 `.frm` 拿列定义 → `userid,username,password,name,idcard,phone,cryptoType`；
5. 直读 `.ibd`：576 个 16 KB 页，42 个 INDEX 页 = 1 个根 + 41 个叶子，合计 **5000 条活记录**；实测记录框架与 `cryptoType` 的逐字段编码规律；
6. 按规范做脱敏 + 哈希输出 UTF-8 CSV，再用 PDF 里 userid 1/2/3 的期望行做**验收**（这一步决定了整篇是“我觉得对”还是“它确实对”）。

## 三、逐步复现

### 3.1 第一步：PDF 文本层（`01_pdf_extract.py`）

不依赖 `pypdf`/`pdfminer`，纯标准库三段式：按 `obj…endobj` 切间接对象 → 对带 `/FlateDecode` 的流做 `zlib.decompress` → 解析字体 `/ToUnicode` 的 CMap（`beginbfchar`/`beginbfrange`），再遍历内容流的 `Tj/TJ` 算子还原文字。

```text
[OK] pdf size = 103931 bytes
[OK] indirect objects = 52
[OK] content streams = 1
[OK] chars = 416 -> solve\pdf_text.txt
```

抽出来的 `pdf_text.txt`（1,107 字节）只有中文，形如：

```text
对数据进⾏处理后，需保存为 / ⽂件，⽂件编码为 / ，列名为
格式参考：
密码得经过 / 加密处理。例如密码是 / ，则进⾏处理后为
```

**这就是本题第一个坑**：看到这种“句子还在、宾语全丢”的输出，第一反应是“值在图片里”。当时的历史会话也是这么判断的，于是转去做图片提取 —— 但真正的答案不在这里。

### 3.2 第二步：ASCII 其实在文字层（关键修正）

回头统计内容流本身：

```text
[obj4] 21947 bytes dict=b'\n<< /Filter /FlateDecode /Length 4539 >>\n'
[obj4] BT count=117 Tf count=117 Tj=117 TJ=0 Do=17
[fonts used] ['C1', 'TT1', 'TT3', 'TT5', 'TT6']
[xobj used] ['Im1', 'Im2', 'Im3', 'Im4']
```

117 次 `Tf` 意味着字体在中文（`C1` = PingFangSC，Type0/Identity-H）与等宽 ASCII（`TT3/TT5/TT6` = Monaco/Menlo/AndaleMono）之间来回切。中文用双字节码查 CMap 没问题；ASCII 用的是**单字节标准编码**，没有 ToUnicode 表，`cmap.get(code)` 返回空，于是整段被丢掉 —— 416 个字符就是这么来的。

把这些字面量直接打出来，规则原文就全了（`Ò`/`Ó` 是等宽字体对“中文引号”的字形映射，本身是 `“`/`”`）：

```text
' csv '                                   ' utf-8'
'userid,username,passw'  'ord,name,idcard,phone'
'userid: '    ' * '   'ÒabÓ'   'Òa*Ó'   'ÒabcdeÓ'   'Òa***eÓ'
'password: '  ' md5 '  'Ò123456Ó'  'Òe10adc3949ba59abbe56e057f20f883eÓ'
'name'        ' sha-1 ' 'Òced07fb42b05a2ed9efa330250e2bb9175f962ceÓ'
'idcard'      'Ò172865199108200356Ó'   'Ò******1991********Ó'
' 4-7 '       'Ò74580417166Ó'          'Ò745****7166Ó'
'userid,username,password,name,idcard,phone'
```

逐条落成规则：

| 字段 | 规则 | 文档里的例子 | 本地复算 |
|---|---|---|---|
| 文件 | 保存为 `csv`，编码 `utf-8`，列名 `userid,username,password,name,idcard,phone` | — | — |
| `userid` | 不脱敏，原样 | — | — |
| `username` | 只保留首位字符，其余用 `*`；仅两字符时只遮最后一位 | `abcde` → `a***e`；`ab` → `a*` | 一致 |
| `password` | 做 `md5` | `123456` → `e10adc3949ba59abbe56e057f20f883e` | `MD5("123456")` 完全相同 |
| `name` | 做 `sha-1` | `张三` → `ced07fb42b05a2ed9efa330250e2bb9175f962ce` | `SHA1("张三")` 完全相同 |
| `idcard` | 只保留年份，其余打 `*` | `172865199108200356` → `******1991********` | 6 星 + 4 位年 + 8 星，与原值等长 18 |
| `phone` | 第 4–7 位用 `*` | `74580417166` → `745****7166` | 前 3 + 4 星 + 后 4，与原值等长 11 |

两条哈希都能本地一击验中（`e10adc…` 是 `123456` 的 MD5，`ced07f…` 是 `张三` 的 SHA1），说明规则表不是抄错的一手资料，而是原文。

### 3.3 第三步：图片 XObject 与“格式参考”截图（`02_pdf_images.py`）

图片确实也要抽 —— 只是作用是**校验**而不是提供规则。PDF 里的 Image XObject 就是裸像素（`/Width /Height /BitsPerComponent /ColorSpace` + FlateDecode），解压后按通道数 reshape 即可：

```text
[obj 17] 2002x194 len=45855 -> inflated 1165164 == need 1165164  -> obj17_2002x194.png
[obj 24] 588x79   len=226   -> inflated 46452   != need 139356  <-- 通道数判断错了
[obj 13] 64x64 bpc=8 /SMask 21                                -> 图标
```

`obj 17` 打开就是一张“格式参考”表格截图，内容与文字层里的三行示例完全一致：表头 `userid|username|password|name|idcard|phone`，三行分别是 `l*******1 / 113db74a… / 795814cf… / ******1988******** / 731****7567` 等等。这张图**反证了 CSV 里就要这 6 列、且排列就是这个顺序**（`cryptoType` 不进 CSV）。

`obj 24` 那行是通道数的坑：`46452 = 588 × 79`，说明它是**单通道灰度**，但 `/ColorSpace` 指向的是 ICCBased 对象，按 RGB 三通道 reshape 只会得到一条黑条 —— 抽图脚本必须支持“按像素数反推通道数”兜底。

### 3.4 第四步：`.frm` 里的列定义

```text
[frm] 12874 bytes  magic=fe010a
  0x1018  b'PRIMARY'
  0x2966  b'InnoDB'
  0x3153  b'userid'      0x315D  b'username'   0x3169  b'password'
  0x3175  b'name'        0x317D  b'idcard'     0x3187  b'phone'
  0x3190  b'cryptoType'
```

七个字段，顺序就是 `userid, username, password, name, idcard, phone, cryptoType`；主键 `PRIMARY` 在 `userid` 上。注意：**`cryptoType` 是库里的字段，但不进交付 CSV** —— 它的作用是告诉你“这一行被怎么编过”。

### 3.5 第五步：直读 `.ibd` —— 页结构

9,437,184 = 576 × 16,384，一页 16 KB。按 `FIL_PAGE_TYPE`（页内偏移 24）统计：

```text
[ibd] 9437184 bytes = 576 pages
page types {8:1 FSP_HDR, 5:1 IBUF_BITMAP, 3:1 INODE, 17855:42 INDEX, 0:531 未分配}
INDEX: level=1 一个（根 page 3，41 条指针），level=0 四十一个（叶 page 4..72），叶子 nrecs 合计 = 5000
```

页内标准位置也对得上：`infimum` 在页内偏移 99，`supremum` 在 112 —— 这说明记录格式是 InnoDB 的 compact 布局，页大小 16 KB 没错。

**第一个异常点**：页头字段（`FIL_PAGE_OFFSET`、`FIL_PAGE_TYPE`、`PAGE_LEVEL`、`PAGE_N_RECS` 等）在本镜像里是**大端**存储的（`page 3` 的 `type` 字节是 `45 BF`，按小端读成 48965，按大端才是 17855）。原生 MySQL 一律小端，所以这份 `.ibd` 是出题脚本合成的镜像 —— 但它刻意保留了 `infimum/supremum` 的位置和页类型枚举，属于“仿真但不完全仿真”。解析器必须先判字节序，再谈其他。

### 3.6 第六步：记录框架（实测出来的，不是查出来的）

叶子页里的记录有非常规律的骨架。把一条记录的原始字节摊开：

```text
07 1a b3 00 00 01 27 | 01 10 | <payload> | 06 18 20 10 28 | 00 00 00 18 00 b3 | 80 00 00 02 | 00 00 00 00
  ^ 7 字节事务标记        ^2 字节    ^ 编码后的字段       ^ 5~6 字节"长度组"  ^ 6 字节元信息   ^ uid(4B,最高位=1) ^ 4 个 0
```

要点三条：

1. 每页记录都以 `07 1a b3 00 00 01 27` 起头（同一批插入，事务号一致），跟着 2 字节前缀；
2. 尾部固定以 `80 | uid(3 字节) | 00 00 00 00` 收口 —— 这个 uid 是**下一条记录**的 uid，所以定位锚点要取“20 字节尾组（6 长度 + 6 元信息 + 8 字节 uid 与零）”，而不是从头往后读；
3. 尾组前面那 5~6 字节长度组，实测对不上本记录的任何字段长度，是合成器留下的噪声，**不能用来定界**（这一点是后面卡死的直接原因）。

按这个锚点扫，41 个叶子页共定位 5,411 个槽位（多于 5,000 是因为 page 4 的 `PAGE_FREE=7899` 里还留着已删记录）。

### 3.7 第七步：`cryptoType` 与逐字段编码

`payload` 的尾部就是编码名，`Base32`/`Base64`/`Base85` 三种；没有编码名的行就是明文。同一条记录的 5 个字段是**分别编码后直接拼接**的：

```text
=== uid=2  ct='Base32' ===
  b32[0] b'L3e83oiCeUDhnTuYnK6Hqy3'          (23B) username
  b32[1] b'GkpZY8O2PCGaleDm'                (16B) password
  b32[2] b'\xe4\xb8\xa5\xe8\x90\x8c\xe9\x98\xb3'  (9B) name = 严萌阳
  b32[3] b'612495199903275975'              (18B) idcard
  b32[4] b'74083020653'                     (11B) phone
```

Base32 每条字段都带 `=` 补齐（40/32/16/32/24 字符），所以按 `=` 切块就能干净地分开 5 段。Base64 与 Base85 就没这么幸运：Base64 的长度是 `4*ceil(n/3)`，字段字节数恰好是 3 的倍数时**不产生填充**；Base85 是 `5*(n//4) + (n%4+1)`，同样可能没有填充信息。于是相邻字段的边界要靠“结构合法性”反推：末尾必须是 18 位身份证 + 11 位手机号，姓名必须是合法 UTF-8 中文，username/password 必须是可打印 ASCII。

### 3.8 第八步：用 PDF 的示例行验收

PDF 里那张“格式参考”表给的是 userid 1/2/3 三行**期望输出**，相当于题目自带的测试用例：

```text
uid=1 ct=Base85  5 项比对 ✓✓✓✓✓   l*******1 / 113db74a… / 795814cf… / ******1988… / 731****7567
uid=2 ct=Base32  5 项比对 ✓✓✓✓✓   L*********************3 / 48263511… / 4ce1fdf1… / ******1999… / 740****0653
uid=3 ct=Base64  5 项比对 ✗✗✓✓✓   username 取到 18 位、MD5 不对；name/idcard/phone 三项中
```

uid=1 与 uid=2 是最强的证据：`MD5(password)` 与 `SHA1(name)` 两个 128/160 位哈希同时撞中，不可能是巧合 —— 说明**抽记录的字节范围、字段切分、解码方式、脱敏规则**四件事全对。uid=3 的 username/password 之所以没中，正是因为 Base64 的填充缺失导致的边界多解（见卡点）。

### 3.9 第九步：产出 `result.csv`

```text
csv bytes = 583798   sha256 = 9705f676…b46278   lines(incl header) = 4495
header    = ['userid','username','password','name','idcard','phone']   列宽={6}
idcard 全形如 ******YYYY******** : True     phone 全形如 3位+****+4位 : True
md5 长度 {32}  sha1 长度 {40}    password 空串行数 = 1179（空串的 MD5 = d41d8cd9…）
```

自带自检规则：**脱敏后的长度必须等于原值长度**（身份证 18、手机 11、md5 32、sha1 40）。星号数量算错，长度立刻对不上，一眼能抓出来。
## 四、关键知识点

| 概念 | 是什么 | 这题为什么用它 | 以后在哪还会遇到 |
|---|---|---|---|
| PDF 内容流 | 页面内容是一串 `Tf/Tj/TJ/Do` 算子，字体按资源名切换 | 中文与 ASCII 混排时，按错资源名查 CMap 会静默丢字（中文靠 `/ToUnicode` 的 `bfchar`/`bfrange`，ASCII 走单字节标准编码） | 所有 PDF 文本抽取、发票/合同解析 |
| Image XObject 裸像素 | `/Width /Height /BitsPerComponent /ColorSpace` + FlateDecode | 截图型“规范”只能抽图看；通道数判断错就出黑条 | 扫描件 OCR、图片型表格提取 |
| InnoDB 页与字节序 | 16 KB 一页，`FIL_PAGE_TYPE=17855` 是 INDEX，level 0 为叶子 | 没有 mysqld 时的唯一取数路径；页头本应小端，本题是大端，解析前必须先探字节序 | 误删表恢复、`.ibd` 离线取证 |
| 记录链与伪记录 | `infimum`(99)/`supremum`(112) 固定位置，`nrecs` 在页头 | 用来校验页大小与记录格式假设 | innodb_ruby、undrop-for-innodb |
| 逐字段编码拼接 | 每个字段单独 Base32/64/85，再首尾相接 | 填充符即分隔符；无填充时边界要靠语义反推 | 弱加密的导出文件、ETL 中间态 |
| 哈希做验收锚点 | MD5/SHA1 是 128/160 位判据 | 只要有一个对得上，整条链就闭合 | 任何“规则 + 数据”双缺失的题 |

## 五、踩坑与陷阱

1. **“关键值在图片里”这个结论是错的。** 历史会话到这里就转向抽图，还把 `pdf_text.txt` 的残缺当成结论写进了任务说明。实际把内容流的 117 个 `Tj` 字面量直接打出来，规则原文一行不少 —— 真正的问题是**字体资源名没跟上**，不是“值不在文字层”。教训：文本残缺先怀疑自己解码，再怀疑文件。
2. **`ColorSpace` 不可信。** `obj 24` 标着 ICCBased，像素数却只有 `588×79`，单通道灰度。按声明 reshape 会得到一条黑条；正确做法是用 `inflated_size / (w*h)` 反推通道数。
3. **页头按小端读，一个页都认不出来。** `type@24` 读成 2048/1280/768 这种数字时，别急着否定文件，先怀疑字节序 —— 换成大端立刻对上 `8/5/3/17855`。
4. **记录头里那些“长度组”是噪声。** 我一开始死磕尾部那 5~6 字节，想把它们解释成 5 个字段的长度表，试了“本行”“下一行”“解码后长度”三种都自相矛盾。最后是靠**语义约束**（18 位身份证 + 11 位手机 + 中文姓名）定界的。

## 六、赛场 20 分钟行动清单

1. `pdfinfo` / 自写脚本抽文本层，看到“保存为 __ 文件”这种空壳，**立刻去数字体资源名与 `Tf` 切换次数**，不要先转图片。
2. 把内容流里所有 `(...)` 字段打印出来 —— 规则往往就藏在这些字面量里（本题连示例值都给了）。
3. 抽 Image XObject，把“格式参考”截图当**验收用例**存好（列名、顺序、行数）。
4. `.frm` 用 `strings` 走一遍拿字段名与顺序；够用了，别硬啃整套 `.frm` 结构。
5. `.ibd` 先看页类型分布与 `nrecs` 总和，拿到“应该有多少行”这个基准数；再用字符串搜索定位第一条记录，**先跑通 3 条**。
6. 挑 `cryptoType` 最简单的那一类（本题是 Base32，填充齐全）先做通，用 PDF 示例行验哈希；哈希一中，整条链就锁死了，最后再啃缺填充的编码。

> 20 分钟还没拿到“一条记录能被 PDF 示例行验证”，就别继续抠结构了：改用 `strings` + 正则先把所有 18 位数字串和 11 位数字串捞出来，先交一份“能对得上列形状”的 CSV。

## 卡点与正解方向

**已确认（全部可复算）**

- 交付物是 UTF-8 的 `csv`，6 列 `userid,username,password,name,idcard,phone`，列名与顺序由文字层字面量与 `obj 17` 截图双向印证。
- 脱敏规则 5 条全部拿到原文，其中两条哈希规则可用文档自带示例一击验证（`MD5("123456")`、`SHA1("张三")`）。
- `person.data` 表 7 个字段，主键在 `userid`；`.ibd` 共 576 页，42 个 INDEX 页（1 根 + 41 叶），活记录 **5000** 条；记录骨架与 `cryptoType` 三种编码全部实测确认。
- 验收：userid=1、userid=2 两行**五项全中**（含 MD5 与 SHA1 双哈希命中）；userid=3 的 name/idcard/phone 三项命中。产物 `result.csv` 4,494 行，列宽、掩码形状、哈希长度自检全通过。

**卡在哪**

1. **无填充编码的字段边界多解。** Base64/Base85 是“定长分组 + 末组补齐可选”，当字段字节数落在特定余数上时，相邻字段的边界在字节流里不可判。uid=3 就是这样：`(6,12,9,18,11)` 与其他若干组合都对尾部的 18 位身份证 + 11 位手机成立，只能靠“哪个更像口令”去猜，一猜就错。全表 **895 行**处于多解状态。
2. **记录头里的 varlen 长度表没解出来。** 尾部那 5~6 字节疑似长度组，与“本行明文长度”“本行编码长度”“下一行长度”三种解释都矛盾 —— 而它本应是唯一能定界的权威信息。
3. 副作用：明文行分不开 `username` 与 `password`（两者都是可打印 ASCII、中间无分隔），暂按“口令为空”处理，导致 1,179 行输出 `d41d8cd9…`。

**正解方向（按性价比排序）**

1. **把 varlen 长度表解出来。** InnoDB compact 记录的定界权威是「5 字节头 + 空位图 + 变长列长度数组」。本题镜像虽然字节序被改成大端、还混入 2 字节前缀与噪声组，但 `infimum/supremum`、`nrecs`、记录链都在原位 —— 按标准 compact 布局逐字段对齐（“变长列按声明逆序、每列 1 或 2 字节”），比继续猜语义靠谱；一旦对上，895 行多解与 1,179 行空口令会一次性消失，也能补满 5,000 行。
2. **用编码长度残差做全局约束。** Base64 周期 3 字节、Base85 周期 4 字节：同一列的“明文字节数 mod 周期”应有稳定分布（口令长度集中在少数几档）。用整列一致性反解边界，比逐行猜强得多。
3. **交叉来源校验。** 同批次的 13 题（`ds-enen`）里那个加密 ZIP 内的 `data.csv` 是 628,623 字节 —— 若两题同源，那边可作为“校验集”反过来验证本表的切分是否合理（5,000 行 × 约 120 字节正好同量级）。
4. **退一步的交付形态。** 无法定界的行列标 `unknown` 并写清依据 —— 数据安全赛道看的是“抽取 + 分类 + 脱敏”的工程闭环与可复现性，不是强行凑满行数。
